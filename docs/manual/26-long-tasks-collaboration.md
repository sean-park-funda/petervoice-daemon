# 26. 장기 작업 관리 & 에이전트 협업

## 핵심 문제

에이전트는 **1턴 대화** 구조다. 유저 메시지 → 에이전트 응답 1회 → 다음 유저 메시지까지 대기. "매뉴얼 38개 문서 최신화해"처럼 여러 단계가 필요한 작업은 1턴 끝나면 멈춘다.

이 문제를 해결하는 세 가지 메커니즘이 있고, 서로 보완한다.

---

## 해결 메커니즘 요약

| 메커니즘 | 용도 | 트리거 | 속도 |
|----------|------|--------|------|
| `/do` | 유저가 요청한 멀티턴 작업 | 유저 명령 | 빠름 (~60초/턴) |
| HeartBeat | 주기적 반복 작업 | 타이머 (30분+) | 느림 |
| Stall Detection | 실수로 멈춘 대화 감지 + nudge | 30분 점검 | 감지만 |

---

## /do 명령어 — 매니저 기반 멀티턴 실행

파일: `scripts/daemon/manager/thread.py` (`_run_deep_task`)

유저가 `/do 작업내용`을 입력하면 ManagerThread가 자동으로 멀티턴 루프를 실행한다. 에이전트가 1턴 끝나면 매니저가 즉시 다음 지시를 주입하여 연속 실행한다.

### 사용법

```
/do 매뉴얼 38개 문서 최신화해        ← 기본 50턴
/do 30 매뉴얼 38개 문서 최신화해     ← 최대 30턴 지정
```

### 실행 흐름 (체크포인트 방식)

```
[턴 1]       유저 원문을 그대로 에이전트에 전달 (매니저가 가공하지 않음)
[턴 2-4]     직접 주입: 에이전트 응답 → 즉시 "이어서 다음 항목을 처리하세요" 주입
             (매니저 Claude 호출 없음 → 오버헤드 최소)
[턴 5]       첫 체크포인트: 매니저가 DONE/CONTINUE/QUESTION 판단 + 유저에게 보고
[턴 6-9]     직접 주입
[턴 10]      체크포인트 ... 반복
[타임아웃]   중단 안 함 → 다음 턴 계속 (3연속 타임아웃만 중단)
[종료]       체크포인트에서 DONE 판단 or max_turns 도달
```

> **체크포인트 조건**: `turn > 1 and turn % 5 == 0` → 턴 5, 10, 15, ...에서만 매니저 개입

### 왜 체크포인트 방식인가

이전에는 매 턴마다 매니저가 3-4회 Claude를 호출했다 (지시 생성 + 진행 요약 + 완료 판단). 반복적 작업에서는 이 판단이 대부분 불필요하다.

```
매 턴 판단 (이전):  38턴 × 3.5회 = ~133회 매니저 Claude 호출
체크포인트 (현재):   7회 체크포인트 = ~7회 (95% 감소)
```

### 매니저 역할 분담

| 단계 | 매니저 | 데몬 |
|------|--------|------|
| 첫 턴 | — (유저 원문 그대로 전달) | 주입 + 응답 대기 |
| 직접 주입 (비체크포인트) | — | "이어서 진행하세요" 자동 주입 |
| 체크포인트 (매 5턴) | DONE/CONTINUE/QUESTION 판단, 유저 보고 | — |
| 완료 | 최종 요약 생성 | 유저에게 전달 |

### 에러 처리

| 상황 | 동작 |
|------|------|
| 1회 타임아웃 | 다음 턴 계속 ("이전 작업이 타임아웃됐습니다. 이어서 진행하세요") |
| 3연속 타임아웃 | 작업 중단 + 유저 알림 |
| 프로젝트 busy | 30초 대기 후 재시도 |
| max_turns 도달 | 유저 알림 ("이어서 하려면 /do로 다시 시작") |

## HeartBeat — 주기적 반복 작업

파일: `scripts/daemon/heartbeat.py`

정해진 간격(최소 30분)마다 에이전트에게 "할 일 확인" 메시지를 주입하는 시스템. `/do`와 달리 장기간 반복 실행에 적합하다.

### 흐름

```
유저: "자율적으로 돌려"
  ↓ 에이전트가 등록
1. docs/HEARTBEAT.md 작성 (작업 체크리스트)
2. POST /api/tasks (태스크 등록, interval_min=30, max_runs=20)
  ↓
HeartbeatThread (매 60초 폴링)
  ↓ due 태스크 발견
"[heartbeat] HEARTBEAT.md 확인하고 처리해줘" 주입
  ↓
에이전트가 HEARTBEAT.md 읽고 다음 미완료 항목 처리
  ↓ 전부 완료 → 태스크 status='done'
```

### /do와의 차이

- **HeartBeat**: 30분 간격, 에이전트 자체가 HEARTBEAT.md 보고 판단, 장기 반복에 적합
- **/do**: ~60초 간격, 매니저가 판단, 일회성 대량 작업에 적합

## Stall Detection — 중단된 대화 감지

파일: `scripts/daemon/health.py`

에이전트가 "잠시만요" 하고 응답 후 실제로는 멈춰 있는 상황을 감지하고 nudge한다.

### 흐름

```
SessionHealthChecker (30분마다)
  ↓
모든 활성 세션의 최근 대화 5건 스니펫 수집 (각 400자)
  ↓
session-manager 프로젝트(Haiku)에 [stall-check 리포트] 전송
  ↓
session-manager가 대화 맥락을 읽고 판단:
  - 자연스럽게 끝난 대화 → 무시
  - "잠시만요" 후 30분+ 침묵 → nudge
  - 유저가 보류 요청 → 무시
  ↓
nudge 필요 시 → [stall-check] 릴레이를 해당 프로젝트에 전송
nudge 불필요 시 → "없음" 한 마디 (토큰 절약)
```

### 왜 Python이 판단하지 않는가

대부분의 대화는 봇 메시지로 끝난다. "완료했습니다"도 "잠시만요"도 둘 다 봇 메시지가 마지막이다. 기계적 임계값으로는 정상 종료와 중단을 구분할 수 없고, 대화 맥락을 이해하는 LLM(session-manager, Haiku)만이 판단 가능하다.

### session-manager 프로젝트

- **Haiku 모델**의 Claude Code 세션
- 세션 건강 관리(2시간 주기)와 stall 감지(30분 주기)를 모두 담당
- `_ensure_session_manager()`가 첫 실행 시 자동 생성 (프로젝트 + 프롬프트 + haiku 모델 설정)

## 에이전트 협업

피터보이스에서 에이전트끼리 협업하는 패턴들.

### Relay — 에이전트 간 메시지 전달

파일: `app/api/relay/message/route.ts`

프로젝트 A의 에이전트가 프로젝트 B에게 메시지를 보내는 단방향 통신.

```
프로젝트 A → POST /api/relay/message → 프로젝트 B의 messages 테이블에 주입
프로젝트 B의 worker가 폴링 → Claude Code 실행 → 필요시 역방향 relay
```

**사용 예**: 코드 리뷰 요청, 작업 결과 전달, stall-check nudge

상세: [11-relay.md](./11-relay.md)

### Summon — 다중 에이전트 리뷰

파일: `scripts/daemon/summon.py`

프로젝트 에이전트의 산출물을 전문가(designer, code-reviewer 등) + 비판자(critic)가 라운드 방식으로 리뷰/개선.

```
유저: "디자이너 소환해서 UI 봐줘"
  ↓
라운드 루프:
  전문가 의견 → 비판자 검토 → 개선 지시 → 전문가 반영 → ...
  ↓
비판자가 [SUMMON_COMPLETE] 선언 or max_rounds 도달 → 종료
결과: docs/summon/summon-{id}.md
```

상세: [22-summon.md](./22-summon.md)

### Manager — 자율 순회 점검

파일: `scripts/daemon/manager/thread.py`

`/do` 외에도 매니저는 설정된 프로젝트를 자율적으로 순회 점검한다.

```
Scout (상태 질문) → Triage (AUTO/ASK/SKIP) → Execute (멀티턴)
```

- `autonomous: true` → 유저 승인 없이 자율 실행
- `autonomous: false` → 유저에게 제안, 승인 대기

상세: [18-manager.md](./18-manager.md)

## 전체 그림: 언제 뭘 쓰나

```
유저가 직접 요청한 대량 작업
  → /do (빠름, 매니저가 멀티턴 자동 실행)

정기적으로 반복해야 하는 작업 (모니터링, 보고)
  → HeartBeat (30분 간격, 에이전트가 HEARTBEAT.md 보고 자율 처리)

에이전트가 응답해야 하는데 멈춰 있을 때
  → Stall Detection (session-manager가 감지, 릴레이로 nudge)

다른 프로젝트 에이전트에게 메시지/요청 전달
  → Relay (단방향 메시지 전달)

산출물에 대해 전문가 리뷰가 필요할 때
  → Summon (다중 에이전트 라운드 리뷰)

프로젝트를 자율적으로 점검하고 싶을 때
  → Manager 자율 순회 (Scout → Triage → Execute)
```
